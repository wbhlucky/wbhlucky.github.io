DitingAgent Agent Loop 复盘：用确定性工作流包住 SDK Agent Loop

用途：代码复盘、面试讲项目、快速恢复架构记忆。

核心认知： DitingAgent 不是简单的“LLM + Tool”，而是“确定性工作流包住 SDK Agent Loop”，再用 Evidence、Budget、Submission、Seal、Validation 把模型的自由行为约束成可审计、可收敛的闭环。

3. Agent Definition vs Session：理解这套架构最关键的一层

3.1 三层结构

Agent Definition / Config
        ↓
Agent Session / Runtime
        ↓
Model + Tool Loop

在本项目里：

ClaudeAgentSdkAgent / QoderAgentSdkAgent
    │
    ├─ skills
    ├─ project_root
    ├─ runtime_config
    └─ memory_context
    │
    ▼
analyze()
    ├─ 新建 MCP server
    ├─ 新建 SDK client / session
    ├─ 新建 submission_state
    ├─ 新建 allowed_tools
    └─ 开始真正的 LLM Tool Loop

所以：

Agent 对象更像“配置载体”；真正的运行状态在 Session / Run 内。

Definition 保存什么？

模型/SDK配置
Skills
project_root
运行规则
允许的工具
memory_context 等

Session / Run 保存什么？

当前 Trace
conversation / messages
tool call history
evidence
budget
submission_state
seal 状态
当前分析进度

可以记成：

Agent = 我是谁、我能做什么；Session = 我这一次正在做什么。

3.2 为什么每次 run 都 new Agent？

不是因为 Agent 很重。

ClaudeAgentSdkAgent.__init__() 只保存少量配置字段；真正有成本的东西是在 analyze() 内按次建立的：

MCP server
SDK client / session
submission_state
allowed_tools
LLM calls / tool calls

因此：

new Agent 对象 ≈ 新建轻量配置对象

真正的大头是：

SDK Session
+ LLM inference
+ token
+ tool execution
+ latency

3.3 为什么项目需要 Factory？

关键不是“Agent 很重”，而是：

Agent 配置是 run-dependent 的。

因为：

Trace / Scenario
    ↓
Skill 路由
    ↓
Agent Config

例如：

cold-start
→ trace-analysis + cold-start-analysis

frame-jank
→ trace-analysis + frame-jank-analysis
→ 若有 perf samples，再加 perf-sample-analysis

所以生产路径每次分析在 analysis.setup 调一次：

DefaultAnalysisAgentFactory.create()
        ↓
本次 Run 专属的 Agent Definition
        ↓
analyze()
        ↓
本次 Run 专属的 SDK Session

resume 时也会重建，因为 analysis.setup 不属于可复用 step。

Factory 的真正职责

根据当前 Trace / Scenario / Skill 上下文，组装正确的 Agent 配置。

不是：

“因为 Agent 很重，所以必须 Factory。”

3.4 Agent 能不能跨 Run 复用？

可以，只要 Agent 本身不持有 run-specific mutable state。

LocalAnalysisAgent() 被 eval 多个 case 复用就是直接证明。

但如果 Skill / Prompt / Tools 会随 Scenario 改变，则需要重新组装 Definition。

因此更准确的工业化表达是：

Agent Definition：可复用
Session / Run：必须隔离
Run State：不应该塞进 Agent Definition

独立 Trace 不共享会话，是为了避免：

Run A 的 evidence / conversation / tool history
            ↓
污染 Run B

3.5 Skill fingerprint 为什么每次算？

流程：

SkillCatalog.require()
    ↓
rglob skill directory
    ↓
read_bytes()
    ↓
SHA256
    ↓
fingerprint
    ↓
manifest.skills

当前 Skill 目录只有几十个文件、几十 KB 量级，重算成本很小。

价值在于可复现 / 可审计：

某次 Run 用了哪个 Skill 版本？
后来 Eval 变了，是不是 Skill 文件改了？

因此这里属于典型的：

用很小的运行时开销换审计和复现能力。

这部分面试一句话

Agent Definition 与 Session 解耦是通用工程模式；本项目因为 Skill 随 Scenario 变化，所以通过 Factory 每次组装轻量 Definition，再为每个分析建立隔离 Session。

4. Trace 和 Evidence：一开始分别是什么？

4.1 TraceHandle

Step 2 产出，核心信息：

database_path
capabilities
trace_id / format / size_bytes / trace_path
baseline_*          # 有 --baseline 时
conversions         # 转换审计

Step 3 注册工具时真正直接用于门控的是：

ToolRegistry(set(trace.capabilities))

其余字段通常被 handler 闭包捕获，真正执行时再用；SQLite repository 也是工具调用时才构造，所以注册阶段几乎零成本。

Trace 是“去哪查、支持什么”的句柄，不是把全部 Trace 数据预加载进内存。

4.2 EvidenceStore

创建时就是空容器：

_evidence = []
_audit = []

工具每次执行再写入：

EvidenceRecord
ToolAuditRecord

并分配：

ev-0001 / ev-0002 / ...

后续 normalize / validate / report 都会读取它，失败时也可以直接落盘：

evidence.json
agent-log.jsonl

Trace 负责“查数据”，Evidence 负责“证明这次分析查到了什么”。

5. Skill：严格按 Scenario 路由

4 个场景与公共 Skill 的关系：

cold-start          → trace-analysis + cold-start-analysis
response-latency    → trace-analysis + response-latency-analysis
completion-latency  → trace-analysis + completion-latency-analysis
frame-jank          → trace-analysis + frame-jank-analysis

若 Trace 中：

perf_sample 表存在 + 真有行

再加：

perf-sample-analysis

所以一次通常是：

2 个 Skill，或 3 个 Skill

Claude / Qoder 的加载差异

传给 Factory / adapter 的首先是 SkillDefinition 元数据，不是 SKILL.md 正文。

Claude

SkillDefinition
→ system prompt / Read 白名单
→ 模型 Read
→ SKILL.md 才真正进入上下文

Qoder

可以把 skills=[name...] 交给 SDK，由 SDK 原生加载。

Claude 路径的 Read hook 还会限制模型只能读本次启用 Skill 目录，防止偷看其他场景方法论。

Scenario 决定场景 Skill；Trace 是否有 perf samples 决定是否加 perf Skill。

6. Capability：不是数据库完整 schema，而是语义开关

inspect() 先查：

SELECT name
FROM sqlite_master
WHERE type IN ('table', 'view')

这里得到的 tables 只是局部变量，不会原样对外输出。

因此：

Capability 是对底层 SQLite schema 的有损、多对一语义投影。

12 类能力的来源

无条件基线

FILE_METADATA
TRACE_DATABASE

baseline 参数决定

BASELINE_METADATA

表存在即可点亮的 7 类

Capability 候选表
PROCESSES process
THREADS thread
SLICES callstack, slice
CPU_SCHEDULING sched_slice, thread_state
IO_EVENTS diskio, file_system_sample, bio_latency_sample, syscall
FRAME_EVENTS frame_slice, actual_frame_timeline_slice, expected_frame_timeline_slice
MARKERS instant, app_startup, task_pool, callstack

判断是候选表集合与实际表集合有交集即可点亮，所以不能从 capability 反推完整 schema。

还要求“表存在 + 真有行”的 2 类

APP_STARTUP_STAGES → app_startup + 有数据
PERF_SAMPLES       → perf_sample + 有数据

目的是防止空表把工具错误放行。

Capability 真正负责什么？

Trace.capabilities
   ↓
ToolRegistry.available()
   ↓
工具可见性

以及：

capabilities
   ↓
ScenarioSkillRouter
   ↓
是否加入 perf Skill

所以它回答：

“这个 Trace 支持哪类分析？”

而不是：

“这个 DB 到底有哪些表、哪些列？”

真正 schema 来自：

Skill reference 文档
+ query_trace_sql
+ repository 运行时列探测

7. Schema 门控：三层

① 表存在
   ↓
capability
   ↓
工具看不看得见

② 特定表是否有数据
   ↓
防空表误放行

③ 工具执行时检查列
   ↓
决定 SQL 怎么写，适配 schema 漂移

所以最短记法：

Capability 决定“看不看得见”；Repository 决定“怎么查”。

8. Preflight：把“模型不该动脑”的调用拿走

8.1 核心原则

参数不需要模型判断的工具调用，就不应该让模型来调。

例如：

get_trace_overview
场景候选工具的第一次全量发现

如果参数只是：

request 字段 + 常量

就应该在 step 4 先执行。

8.2 为什么提前跑？

否则模型开局会花工具调用去做低价值工作：

耗 token
耗 latency
耗 tool budget
增加抄错参数 / 忘调 / 重复调 / 乱造参数的概率

典型的 completion-latency 是两阶段：

第 1 次：preflight
 target_ipid = 0
 → 全量发现候选

第 2 次：Agent
 target_ipid = 非零
 → 对最终应用进程补充精查

这里：

第一次不需要判断，第二次需要模型从候选里选目标，二者职责不同。

8.3 preload 不是特殊旁路，而是 invoke

def preload(name, arguments=None):
    result = self.invoke(name, arguments)
    self._preloaded_results.append(result)
    return result

所以预载：

  1. 真实消耗 invocation / tool budget
  2. 真实写 Evidence + audit
  3. 真实受到 per-tool limit、seal 等约束

因此：

preloaded evidence 不是 prompt 背景资料，而是正式 Evidence。

它会进入：

EvidenceStore
→ normalize
→ validate
→ evidence.json

8.4 Budget 体现了“预载 + 补充取证”的分工

典型配置：

get_trace_overview                         limit = 1
inspect_problem_window_candidates          limit = 1
inspect_completion_latency_candidates     limit = 2

于是可以做到：

确定性的第 1 次 → preflight
需要判断的第 2 次 → Agent

这不是 prompt 劝说，而是预算 + Submission Policy 共同构成的硬约束。

8.5 Readiness Gate：当前主要是透明化契约，不是实际输入拦截器

这里最容易讲错。

当前 _completeness_gaps() 对用户输入的缺失只产生：

target_process     → info
refresh_rate_hz    → warning
problem_interval   → warning

而 blocking() 只看：

severity == "error"

所以：

缺 target-process
缺 refresh-rate
缺 problem interval
        ↓
当前都不会因为“缺输入”而阻塞

生产路径里真正可能产生 error 的来源是：

tool_available = False

即场景要求的候选工具不在 tools.names()。

但当前这些场景候选工具的 required_capabilities 都只是：

{TRACE_DATABASE}

而 TRACE_DATABASE 是 DB 能打开就会存在的基线能力。

因此生产中通常：

tool_available = True
→ 无 error gap
→ ready = True

所以准确定位是：

Readiness Gate 现在是契约骨架 + 透明化 / 审计机制，而不是主要的输入拦截器。

它现在真正做三件事

1. 显式记录系统假设

例如没有 refresh rate 时：

使用 60Hz 默认值
+ default_applied = true
+ warning

problem interval 也可以按规则从 Trace 推导。

2. 生成可审计的 PreflightReport

记录：

ready
tool
gaps
preloaded_results

并落盘：

preflight-report.json

3. 给 UI 提供结构化状态

事件可携带：

ready
tool_available
gap_count

为什么 Gate 仍然有价值？

因为骨架已经存在：

InputGap + severity
→ blocking()
→ ready
→ structured failure path

未来想收紧准入，只需要把某些 warning 提成 error，或者让工具声明更细的 capability，不必重写主编排。

8.6 Preloaded evidence 如何进入模型？

build_user_prompt(..., preloaded_evidence=...) 会把预载结果注入 user prompt，并告诉模型：

这些结果与工具返回值具有相同证据效力
不要重复调用同参数发现工具

所以模型并不是“从零开始”：

用户请求
+ memory_context
+ preloaded_evidence
+ Skill 方法论

8.7 Local adapter

Claude / Qoder / OpenAI 等路径声明需要 preflight；local 不依赖这层，但会兜底：

overview = tools.last_result("get_trace_overview")
if overview is None:
    overview = tools.invoke("get_trace_overview")

即：优先复用预载结果，没有才现场补调。

9. 真正的 Agent Loop：Step 5

项目不是手写一个简单：

while True:
    llm()
    tool()

而是：

Agent SDK
   ↕
LLM
   ↕
MCP Tools

应用层控制边界、权限、预算、提交和收敛；SDK 负责具体的会话和工具循环。

9.1 Skill / Tool 权限

系统提示会要求模型先读取本次启用的 Skill，再进入 Trace 工具分析。

典型允许：

Read
Trace MCP tools

典型禁止：

Bash / Edit / Write / Grep / WebFetch / Task

所以这是专用 Trace Agent，不是通用 Coding Agent。

10. 一次 Tool Call 到底经过什么？

LLM
 ↓
ToolRegistry.invoke()
 ↓
预算 / per-tool limit / seal
 ↓
handler
 ↓
SQLite repository
 ↓
EvidenceStore
 ├→ 完整结果
 └→ audit
 ↓
agent_tool_payload
 ↓
LLM

关键设计：

Evidence 保存完整结果；模型只拿压缩视图。

这样上下文不会被大量原始数据撑爆，但审计和后处理仍拿得到完整证据。

11. Tool Budget：真正的硬限制

Prompt 里可以告诉模型：

普通工具 ≤ 14 次
query_trace_sql ≤ 6 次

但真正的硬约束来自 ToolRegistry.invoke()：

总 budget
per-tool limit
perf 独立预算

超限时抛 ToolBudgetExceeded，并把“基于现有 Evidence 尽快提交”之类的指令反馈给模型。

Prompt 是软约束；Registry budget 是 runtime guardrail。

12. Submission：Agent 的真正“交卷闸门”

模型必须显式调用：

submit_analysis_result

然后经过：

1. EvidenceSubmissionPolicy
2. Schema
3. validate_analysis()

EvidenceSubmissionPolicy 的作用

它不是检查“格式像不像”，而是检查：

结论所需的关键证据到底有没有真正取到。

例如 completion-latency：

必须有最终非零 target_ipid 的证据

存在 perf samples 时：

必须 inspect_perf_profile
并限定到线程级 TID

reject 怎么办？

不会直接结束：

submit
 ↓
reject
 ↓
精确 instruction
 ├→ 缺哪个证据
 ├→ 应该调哪个工具
 └→ 应该传什么参数
 ↓
继续当前会话
 ↓
再次 submit

这才是真正的 Agent repair loop。

13. Seal：为什么 accepted 后马上封盘？

accepted = true
      ↓
registry.seal()
      ↓
所有后续工具调用失败

目的：阻止：

提交
→ 又取证
→ 又修改结论

所以：

accepted = 证据窗口封盘。

这让“交卷”成为真正的状态边界，而不是一个普通函数调用。

14. 两种 Repair：千万不要混

14.1 Submission Reject Repair

原因：证据不够
→ 允许继续调工具
→ 补证据
→ 再 submit

14.2 Parse Repair

如果 SDK 返回结果解析失败：

submission_state
 ↓
structured_output
 ↓
text_blocks 中倒序找 JSON

仍失败时，在满足条件下进入最多 3 轮的输出修复，并受 token / time 双预算约束。

此时工具已经 seal。

因此：

Parse Repair
→ 只能基于已有 Evidence 修正结构化结果
→ 不能再造新证据

最短记忆

Submission Repair = 补证据；Parse Repair = 修输出。

15. Step 6～8：LLM 输出不是最终真相

LLM
 ↓
Evidence-backed result
 ↓
Normalize
 ↓
Validate
 ↓
Report

Normalize

从 Evidence 确定性回填已知大字段，避免 LLM 手工复制事实数据。

Validate

最终做数值、结构、时间边界等校验；失败会留下 rejected-findings.json。

因此：

模型负责提出分析，代码负责最终验收。

_remember_episode()

整体：

Memory 不替代 Agent Loop，它负责跨 Run 的经验积累。

19. 全项目最重要的 8 个工程思想

① 确定性工作给代码，语义判断给模型

② Capability 做工具粗筛，不承担完整 schema

③ Skill 提供分析方法论，Scenario 决定 Skill

④ Evidence 与模型上下文分离
   完整证据留存，模型拿压缩视图

⑤ Prompt 给预算预期，Registry 做硬预算

⑥ Submission 强制证据充分性，不能只看“模型输出得像不像”

⑦ Accept 后立即 Seal，建立不可逆的交卷边界

⑧ Normalize / Validate 在模型之后再次验收

20. 面试高频问答：最短版本

Q1：为什么 get_trace_overview 不让模型自己调？

因为它属于确定性、无判断的首次发现；preflight 先执行，可以减少 token / latency / tool budget，并消灭参数错误和重复调用。

Q2：preload 算不算假的 Evidence？

不算。它直接走 invoke()，真实消耗预算、写 Evidence、写 audit，和模型调用具有同样的证据效力。

Q3：Readiness Gate 是不是“缺输入就失败”？

当前不是。用户输入缺失主要是 info / warning；生产里的 error 分支主要来自工具不可用，而当前场景候选工具都只要求 TRACE_DATABASE，所以基本不会触发。它当前更偏透明化 / 审计契约。

Q4：Capability 是数据库 schema 吗？

不是。是对底层 schema 的语义化、有损投影，用于工具和 Skill 门控。

Q5：模型怎么知道真正 schema？

Skill reference + query_trace_sql + repository 运行时列探测。

Q6：Skill 是不是全加载？

不是。公共 trace-analysis + 1 个场景 Skill + 可选 perf-sample-analysis。

Q7：为什么每次要创建 Agent？

不是因为 Agent 重，而是 Skill / 配置随 Scenario 变化，需要每次组装一个轻量 Agent Definition；真正的 SDK Session 每 Run 隔离。

Q8：Agent 能不能跨 Run 复用？

可以，只要不持有 run-specific mutable state。当前项目的 Local Agent 就这么复用。

Q9：为什么 submit 后还要 seal？

为了防止 accepted 后继续取证、继续改结论，形成真正的封盘边界。

Q10：为什么有两种 repair？

Submission reject 是“证据不够，要继续取证”；Parse repair 是“证据已经够，只修输出结构”。

21. 最终背诵版

DitingAgent 是一个“确定性工作流 + LLM Agent”的 Trace 分析系统。先把 htrace 转成 SQLite，再用 capability 做工具粗筛、按 Scenario 路由 Skill；Agent Definition 只保存配置，真正的 Session / Evidence / Budget / Submission State 都属于单次 Run。进入 Agent 前，preflight 先完成所有不需要模型判断的首次发现，并生成透明的 readiness contract。进入 SDK Loop 后，模型通过 MCP 调 Trace 工具，完整结果进入 EvidenceStore，模型只拿压缩视图；工具预算由 Registry 硬限制，模型必须通过 Submission Policy 证明关键证据已经取到，提交成功后立即 Seal。最后由 Normalize 和 Validator 做确定性验收，再 Render 成报告，并把本次经验写回 Memory。

最核心的一句话

Definition 可复用，Session 要隔离；确定性的事情留给代码，需要语义判断的事情留给模型；最后用 Evidence、Budget、Submission、Seal、Validation 把模型约束在一个可审计、可验证、可收敛的闭环里。
