Agent Skill 完整理解：从 SKILL.md 到渐进式加载的能力包设计

1. Skill 是什么

Skill 是 Agent 的一种可复用专业能力包，核心入口是 SKILL.md。

一个 Skill 通常是一个目录：

cold-start-analysis/
├── SKILL.md
├── references/
├── scripts/
├── assets/
└── agents/
    └── openai.yaml

其中真正定义 Skill 核心行为的是 SKILL.md。

2. SKILL.md 是干什么的

SKILL.md 是 Skill 的核心定义 + Agent Instructions。

典型结构：

---
name: cold-start-analysis
description: Analyze HarmonyOS app cold-start performance.
---

# Workflow

1. 获取 Trace
2. 分析启动阶段
3. 检查主线程
4. 定位耗时瓶颈
5. 结合性能知识判断根因
6. 输出分析结果

它主要回答三个问题：

① 我是谁

name: cold-start-analysis

② 什么时候应该使用我

description: Analyze HarmonyOS app cold-start performance.

Agent 可以先通过 name + description 判断当前任务是否和这个 Skill 匹配。

③ 加载我以后应该怎么干活

就是 SKILL.md 的正文，包括：

  • Workflow
  • Rules
  • Instructions
  • Examples
  • 输出要求等

所以可以记成：

`SKILL.md = 给 Agent/模型看的“技能说明书 + 操作手册”。

3. references/ 是什么

references/ 是 Skill 的参考知识库。

例如：

references/
├── smartperf-event.md
├── jank-patterns.md
├── startup-patterns.md
└── harmonyos-performance.md

这些不是 Skill 本身，而是：

Skill 工作过程中需要查阅的专业资料。

例如 SKILL.md 可以规定：

如果发现 APP_COMPONENT_LOAD 耗时异常，
读取 references/startup-patterns.md，
根据其中的模式判断可能原因。

所以：

SKILL.md
    ↓
告诉 Agent “什么时候/为什么/怎么用”

references/
    ↓
提供 Agent “分析时需要知道的知识”

Reference 需要单独写 metadata 吗？

通常不需要。

直接：

references/
├── startup-patterns.md
└── jank-patterns.md

然后在 SKILL.md 里说明它们分别干什么即可。

只有当 reference 数量特别大，需要自动检索、分类、权限控制、版本管理等，才有必要自己建立额外的 metadata/index。

4. scripts/ 是什么

scripts/ 是 Skill 的可执行资源。

例如：

scripts/
├── query_trace.py
├── calculate_frame_time.py
└── extract_sqlite.py

它和 references/ 最大的区别：

references/
    → 给 Agent “知识”

scripts/
    → 给 Agent “执行能力”

例如：

SKILL.md：

1. 使用 query_trace.py 获取目标线程数据
2. 使用 calculate_frame_time.py 计算掉帧情况
3. 根据 references/jank-patterns.md 判断根因

所以可以简单记：

Reference = Read

Script = Execute

同样，script 通常不需要自己再写一套 metadata。

5. assets/ 是什么

assets/ 是 Skill 可以携带的其他资源。

例如：

assets/
├── report_template.html
├── example_trace.json
└── architecture.png

可以理解为：

Skill 执行过程中需要用到的模板、示例、图片等资源。

它不是 Skill 核心逻辑。

6. agents/openai.yaml 是什么

这是最容易和 SKILL.md 混淆的地方。

最简单的理解：

SKILL.md 定义 Skill 本身；agents/openai.yaml 定义这个 Skill 如何接入 OpenAI 的 Agent/Plugin 体系。

它不是 Skill 的第二份 instructions。

① 声明 Skill 依赖的工具

例如 Skill 需要 SmartPerf MCP：

cold-start-analysis
        ↓
需要 SmartPerf MCP
        ↓
openai.yaml 声明这个依赖

配置的核心含义类似：

dependencies:
  tools:
    - type: mcp
      value: smartperf
      description: Analyze HarmonyOS SmartPerf traces
      transport: streamable_http
      url: https://example.com/mcp

表达的是：

这个 Skill 干活需要 SmartPerf 这个 MCP 工具，Agent 环境需要把这个工具提供给它。

而 SKILL.md 负责：

拿到 SmartPerf 后：
1. 获取 Trace
2. 分析 APP_COMPONENT_LOAD
3. 检查主线程
4. 定位冷启动瓶颈

因此：

openai.yaml
    ↓
“给我什么工具/依赖”

SKILL.md
    ↓
“拿到这些工具后具体怎么干活”

② 配置 Skill 在产品里的展示

例如：

interface:
  display_name: "冷启动性能分析"
  short_description: "分析 HarmonyOS App 冷启动性能"
  default_prompt: "帮我分析这个 App 的冷启动 Trace"

它表达的是：

用户在 OpenAI 产品里看到这个 Skill 时，叫什么、显示什么简介、默认 prompt 是什么。

因此：

SKILL.md
→ 给模型看的 Skill 定义

openai.yaml
→ 给 OpenAI 集成/产品层看的配置

7. openai.yaml 是不是必须的

不是。

如果你的 Skill：

  • 不需要特殊 OpenAI 集成
  • 不需要声明 MCP/tool dependency
  • 不需要特殊 interface 配置

完全可以：

cold-start-analysis/
├── SKILL.md
├── references/
└── scripts/

不需要：

agents/
└── openai.yaml

所以：

没有特殊 OpenAI 集成需求时，openai.yaml 可以不存在。

8. Skill 的完整生命周期

用户任务
   ↓
Agent 看 Skill 的 name + description
   ↓
判断：
“这个 Skill 和当前任务相关吗？”
   ↓
相关
   ↓
加载 SKILL.md
   ↓
按照 SKILL.md 的 workflow 执行
   ↓
┌───────────────┬────────────────┐
↓               ↓                ↓
references/    scripts/        tools/MCP
查知识          执行动作          外部能力
   ↓               ↓                ↓
   └───────────────┴────────────────┘
                   ↓
                得到结果
                   ↓
                输出答案

9. 放到 Trace Agent 里

你的 Trace Agent 可以设计成：

skills/
│
├── cold-start-analysis/
│   ├── SKILL.md
│   ├── references/
│   │   ├── startup-patterns.md
│   │   └── smartperf-events.md
│   └── scripts/
│       ├── query_trace.py
│       └── analyze_startup.py
│
├── jank-analysis/
│   ├── SKILL.md
│   ├── references/
│   │   └── jank-patterns.md
│   └── scripts/
│       └── analyze_frame.py
│
└── ipc-analysis/
    ├── SKILL.md
    └── references/
        └── ipc-patterns.md

运行时：

用户：
“帮我分析这个小红书直播卡顿”
        ↓
Skill Registry
        ↓
发现 jank-analysis
        ↓
加载 jank-analysis/SKILL.md
        ↓
按照 Skill workflow
        ↓
读取 references/jank-patterns.md
        ↓
执行 scripts/analyze_frame.py
        ↓
调用 MCP / Trace Tool
        ↓
输出：
卡顿位置
→ Evidence
→ CPU/调度/锁/IPC...
→ Root Cause

10. Skill、Tool、MCP、Reference、Script、Memory 的区别

东西 解决什么问题
Skill 怎么完成一类任务
Tool 执行一个具体动作
MCP 标准化地把 Tool/资源提供给 Agent
Reference 完成任务时需要查的知识
Script 可以直接执行的程序
Memory Agent 过去记住了什么

例如：

Skill：
“怎么分析冷启动”

Tool：
“查询 Trace 数据”

MCP：
“把 Trace 查询工具以标准协议提供给 Agent”

Reference：
“APP_COMPONENT_LOAD 是什么”

Script：
“执行 SQL 查询”

Memory：
“上一次分析这个 App 时发现主线程 CPU 竞争”

12. 最终记住这 6 句话

  1. Skill 是 Agent 的一种可复用专业能力。
  2. SKILL.md 是 Skill 的核心入口，负责告诉 Agent“我是什么、什么时候用、具体怎么做”。
  3. references/ 放知识资料，scripts/ 放可执行程序，都是 Skill 的辅助资源。
  4. Reference/Script 通常不需要单独写 metadata，在 SKILL.md 中说明怎么使用即可。
  5. agents/openai.yaml 不是 Skill 本身，而是 OpenAI Agent/Plugin 集成层的配置，例如工具依赖、界面展示等；没有这些需求可以不写。
  6. Skill ≠ Tool：Skill 负责“怎么完成任务”，Tool 负责“执行具体动作”。

对 Trace Analysis Agent 的第一版建议

先做：

Skill Registry
+
SKILL.md
+
references/
+
scripts/
+
MCP Tools

先不要为了架构完整强行加入：

openai.yaml
Resource Registry
Skill Metadata DB

等 Skill 数量和运行复杂度真正上来，再增加这些工程层。

13. 不同资源“什么时候加载”

这是理解 Skill 最关键的一点：不是 Skill 目录里的所有东西一开始都加载。

典型的渐进式加载可以理解为：

用户任务
   ↓
① Skill Discovery
   ↓
只看 SKILL.md 的 name + description
   ↓
判断是否相关
   ↓
② Skill Activation
   ↓
加载完整 SKILL.md
   ↓
根据 workflow 判断需要什么资源
   ↓
┌──────────────┬──────────────┬──────────────┐
↓              ↓              ↓
references     scripts        tools/MCP
按需读取       按需执行        按需调用

① 什么时候加载 SKILL.md？

分两层：

Discovery 阶段

Agent 不需要一开始把所有 Skill 的完整内容都读进上下文。

通常先获取：

name: jank-analysis
description: Analyze HarmonyOS app frame jank and dropped frames.

Agent 根据用户任务判断：

“用户现在是在分析卡顿，这个 Skill 相关。”

Activation 阶段

确认需要这个 Skill 后，再加载完整：

SKILL.md

然后 Agent 才知道：

具体分析流程
规则
约束
应该读取哪些 reference
应该调用哪些 script/tool
输出格式

所以：

name + description：用于发现/路由 Skill。

完整 SKILL.md：Skill 被选中后加载，用于真正执行。

② 什么时候加载 references/？

按需加载。

不是：

用户一开始提问
↓
把 references/ 下面所有几十个文件全部塞进 Context

而应该是：

用户：
“分析这个 Trace 为什么掉帧”

        ↓

加载 jank-analysis/SKILL.md

        ↓

SKILL.md：
“如果需要判断常见掉帧模式，
读取 references/jank-patterns.md”

        ↓

Agent 判断确实需要

        ↓

读取：
references/jank-patterns.md

例如：

references/
├── jank-patterns.md
├── cpu-contention.md
├── ipc-patterns.md
└── rendering.md

如果这次分析发现明显是 CPU 竞争：

读取 cpu-contention.md

而不是把：

ipc-patterns.md
rendering.md

全部读取。

所以：

Reference = 根据当前任务/Workflow 按需读取的知识。

③ 什么时候执行 scripts/？

也是按需执行。

例如：

scripts/
├── query_trace.py
├── calculate_frame_time.py
└── analyze_cpu.py

用户问：

“帮我计算这个 Trace 的掉帧率。”

Agent 加载 Skill 后发现：

SKILL.md：

如果需要计算掉帧率，
执行 scripts/calculate_frame_time.py

于是：

用户任务
   ↓
加载 SKILL.md
   ↓
发现需要计算掉帧率
   ↓
执行 calculate_frame_time.py
   ↓
拿到结果

如果这次任务完全不需要计算帧率：

calculate_frame_time.py

就不会执行。

所以：

Script = Skill 执行过程中，根据 workflow 按需调用的程序。

④ 什么时候调用 Tool / MCP？

同样是按需调用。

例如：

Trace Agent
    ↓
需要读取 .htrace
    ↓
调用 SmartPerf MCP
    ↓
获得 Trace 数据

如果 Skill 需要：

查询线程
查询调度
查询 CPU

才调用对应 Tool。

因此：

Skill
 ↓
决定“我要完成什么任务”
 ↓
Tool/MCP
 ↓
真正执行具体动作

⑤ agents/openai.yaml 什么时候加载？

这个和上面几个不太一样。

它主要属于：

OpenAI 集成/运行环境的配置层。

它不是 Skill 执行过程中为了分析 Trace 才去读取的 reference。

例如 OpenAI 集成环境在加载这个 Skill 时，需要知道：

这个 Skill 有没有声明 MCP dependency？
这个 Skill 的 interface 怎么配置？

于是读取：

agents/openai.yaml

因此可以简单理解：

SKILL.md
→ Agent 执行 Skill 时需要

references/
→ 执行过程中需要知识时加载

scripts/
→ 执行过程中需要程序时运行

MCP/Tool
→ 执行过程中需要外部能力时调用

openai.yaml
→ OpenAI 集成/配置阶段使用

14. 一个完整的 Trace Agent 加载过程

假设目录：

jank-analysis/
├── SKILL.md
├── references/
│   ├── jank-patterns.md
│   ├── cpu-contention.md
│   └── ipc-patterns.md
├── scripts/
│   ├── query_trace.py
│   └── calculate_frame_time.py
└── agents/
    └── openai.yaml

用户说：

“帮我分析小红书世界杯直播为什么卡顿。”

Step 1：Skill Discovery

Agent 先看到：

name: jank-analysis
description: Analyze HarmonyOS app frame jank and dropped frames.

发现和“卡顿”高度相关。

↓

Step 2：加载完整 SKILL.md

得到：

1. 获取 Trace
2. 定位卡顿时间段
3. 计算帧耗时
4. 分析主线程
5. 判断 CPU / 调度 / IPC / Render 等原因
6. 输出 Evidence + Root Cause

↓

Step 3：调用 Tool/MCP

需要读取 Trace：

SmartPerf MCP

↓

Step 4：执行 Script

发现需要计算帧耗时：

scripts/calculate_frame_time.py

↓

Step 5：按需加载 Reference

发现主线程 CPU 负载很高：

references/cpu-contention.md

于是读取它。

如果没有发现 IPC 问题：

references/ipc-patterns.md

就不需要读取。

↓

Step 6：输出结果

卡顿时间：
xxx

Evidence：
主线程连续执行 xxx ms

Metrics：
Frame duration = xxx ms

Root Cause：
CPU contention / main-thread computation

Conclusion：
...

整个过程中并不是：

启动 Agent
 ↓
把整个 Skill 目录所有文件全部加载

而是：

先发现 Skill
    ↓
加载 Skill 指令
    ↓
按照指令
    ↓
按需加载 Reference
    ↓
按需执行 Script
    ↓
按需调用 Tool/MCP

这就是 Progressive Disclosure / 渐进式加载 的核心思想。

15. 最终记忆表

资源 什么时候使用/加载 作用
name + description Skill Discovery 判断是否应该使用这个 Skill
完整 SKILL.md Skill 被选中后 告诉 Agent 怎么完成任务
references/ Workflow 判断需要知识时 提供专业知识
scripts/ Workflow 判断需要执行程序时 执行确定性操作
Tool / MCP Workflow 判断需要外部能力时 查询/操作外部系统
agents/openai.yaml OpenAI 集成/配置阶段 声明集成配置、依赖、interface 等
Memory Agent 需要历史经验/上下文时 提供过去的记忆

最重要的一句话

Skill 不是“把一个目录全部塞给模型”，而是“先通过 metadata 找到 Skill，再加载 SKILL.md，然后由 SKILL.md 决定什么时候按需读取 reference、执行 script、调用 Tool/MCP”。
