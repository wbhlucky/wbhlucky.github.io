报告自动生成复盘：Agent 出结论，代码出页面

一、核心设计原则

Agent 负责回答"Trace 到底有什么问题、为什么有问题"；报告系统负责把这个答案 + Trace 数据库里的事实，重新组织成一个 HTML 页面。

两个关键认知：

  1. HTML 不是 Agent 生成的。Skill 也不是生成 HTML。
  2. Agent 产出结构化诊断结果，SQLite 保存原始/计算后的性能数据，Projection 把两者拼成"页面数据"，Jinja + JS 再把页面数据变成 HTML。

二、Skill 的真正职责

Skill 不只是约束"输出格式"，还约束 Agent 的分析方法和内容标准。

Skill 规定：

  • Agent 怎么分析（分析方法）
  • 什么算证据（证据标准）
  • Finding 要包含什么（内容标准）
Skill
  ↓
规定 Agent 怎么分析、什么算证据、Finding 要包含什么
  ↓
Agent + LLM
  ↓
输出结构化 AnalysisResult

Skill 文件（如 report-standardCN.md）实际定义的是：

  • 必须有严重性（severity）
  • 必须说明状态（observed / suspected / confirmed）
  • 必须有证据（evidence_ids）
  • 必须有推理链（evidence → analysis → conclusion）
  • 必须有建议（recommendation）
  • 必须有回归验证方法（validation）
  • 已确定问题区间时提供 problem_interval

三、完整链路总览

Skill
  ↓
规定 Agent 怎么分析、什么算证据、Finding 要包含什么
  ↓
Agent + LLM
  ↓
输出结构化 AnalysisResult
  ↓
Validation
  ↓
校验字段、状态、证据引用、置信度、problem_interval 等
  ↓
校验通过
  ↓
固定的 Python 代码
  ↓
读取：
  ① Agent 的 AnalysisResult
  ② Evidence
  ③ SQLite 里的 Trace 数据
  ↓
ProjectionBuilder
  ↓
自动计算 timeline / perf / frame / flame graph 等报告数据
  ↓
Jinja2 固定模板
  ↓
report.html

四、Agent 与固定代码的职责分工

Agent 决定"结论是什么"

例如：

主线程 CPU 负载过高，导致关键窗口掉帧。

Agent 产出：

{
  "problem_interval": { "start": 12.3, "end": 12.8 },
  "finding": "主线程计算负载过高",
  "evidence_ids": ["E10", "E11"],
  "severity": "high",
  "confidence": 0.93,
  "recommendation": "降低主线程计算负载"
}

固定代码决定"怎么把这个结论展示出来"

自动生成报告结构：

摘要
  ↓
问题区间
  ↓
时间线
  ↓
帧率
  ↓
主线程热点
  ↓
火焰图
  ↓
证据
  ↓
建议

报告不是只根据 Agent 输出生成的

Agent 输出
    +
SQLite Trace 数据
    +
Evidence
    ↓
固定代码 Projection
    ↓
HTML

例如 Agent 只告诉系统 problem_interval = 12.3s ~ 12.8s，Projection 会自己去 SQLite 查：

  • 12.3 ~ 12.8s 有哪些线程？
  • 哪些线程在运行？
  • CPU 怎么占用？
  • 发生了哪些帧？
  • 有哪些热点？

然后把这些数据画进报告。

五、系统四层架构

第一层：Agent 分析层

回答："这个 Trace 有什么问题？"

负责：

  • LLM 推理
  • Skill 指导分析方向
  • Tool 查询数据
  • Evidence 收集
  • Finding 形成
  • AnalysisResult 输出

第二层：数据投影层（Projection）

回答："为了展示这个分析结果，页面需要哪些数据？"

负责：

  • ProjectionBuilder 读取 AnalysisResult + Evidence + SQLite
  • 确定性地计算 timeline / perf / frame / flame tree
  • 整理为页面所需的数据结构（Report View Model）

Projection = 把内部数据"投影"为报告视图模型

第三层：HTML 渲染层

回答："把这些数据塞到 HTML 里。"

负责：

  • Jinja2 模板渲染
  • 将数据嵌入 HTML 模板
  • 输出 report.html

第四层：浏览器交互层

回答："用户打开网页之后，怎么交互和画图？"

负责：

  • JavaScript 读取 REPORT 数据
  • Canvas 绘制时间线、火焰图
  • Tooltip、Zoom、Filter、Drawer 等交互

六、数据源双源模型

数据源 A：Agent（诊断结论）

提供：

  • summary
  • findings
  • severity
  • confidence
  • recommendation

数据源 B：SQLite（真实 Trace 数据）

提供：

  • thread execution
  • CPU
  • frame jank
  • startup module
  • scheduling
  • IPC
  • render

Projection 是中间的"拼接层"

             ┌─────────────┐
             │ Agent 输出   │
             │ Analysis    │
             └──────┬──────┘
                    │
                    ▼
              Projection
                    ▲
                    │
             ┌──────┴──────┐
             │ SQLite      │
             │ Trace事实    │
             └─────────────┘

七、Evidence 证据链

Evidence 是 Agent 分析过程中的"证据链"：

E1  线程 MainThread 在 120ms 内占用 CPU
E2  该窗口发生 3 次 VSync Miss
E3  MainThread 执行某函数 85ms

Agent 结论：主线程高负载导致掉帧
    ↓
finding → E1, E2, E3

系统有 EvidenceIndex，可根据 evidence ID 快速找到对应证据。

Projection 也要读 Evidence，因为有些页面内容不是直接查 SQLite 就够的——例如 Agent 做过什么分析、中间计算结果等，这些信息保存在 Evidence 中。

八、Validation 校验机制

LLM 输出不能直接相信。

Validation 检查：

  • 字段完整性（title、severity、status、confidence、evidence_ids 等）
  • 字段合法性（如 confidence 必须在 0~1 之间）
  • 证据引用正确性（避免同一个 evidence 被多个 finding 重复引用）

校验不通过：

  • 返回 rejected-findings.json + AnalysisValidationError
  • report.html 不会生成

校验通过才进入报告生成阶段。

九、ProjectionBuilder 详解

为什么代码量大（3887 行）？

因为它承担了大量"确定性计算"：

  • 查询线程
  • 筛选线程
  • 计算时间区间
  • 选择 focus thread
  • 计算热点
  • 构造火焰图树
  • 构造时间线
  • 计算启动模块排序
  • 计算帧信息

这些都不应该交给 LLM，本质是报告的数据工程层。

Timeline 类型决定逻辑

有没有 completion_latency？
  → 是：完成时延时间线
  → 否：有没有 cold_start？
    → 是：冷启动时间线
    → 否：有没有帧率证据？
      → 是：掉帧时间线
      → 否：available = false

页面类型不是模型临时决定的，而是 Projection 根据已有数据决定的。

图表数据是渲染时重新查数据库

AnalysisResult 里面不会塞大量原始数据（5000个线程事件、3000个CPU采样、1000个frame），模型只负责"哪里有问题"。报告图表自己需要"这个问题区间里到底发生了什么"，因此由 Projection 在渲染时重新查 SQLite 计算。

十、Renderer 与 Jinja2

Renderer 非常薄（约 75 行）

因为它不负责分析，只负责把已经准备好的数据塞进 HTML 模板：

数据 → Jinja2 → HTML

Jinja2 是服务端 HTML 模板引擎

模板中写 {{ analysis.summary }}，渲染时替换为实际值。

REPORT 数据对象

Renderer 最终会在 HTML 中注入一个 JavaScript 对象：

const REPORT = {
    "timeline": {...},
    "perf": {...},
    "startup_modules": {...}
};

这个 REPORT 就是 Projection 生成的页面数据。

浏览器端可视化

Browser → JavaScript → 读取 REPORT → 画图

renderTimeline(REPORT.timeline) → createCanvasTimeline() → Canvas → 画时间线
REPORT.perf → createPerfFlame() → Canvas → 火焰图

十一、Case 目录文件说明

系统保存"这个分析任务完整的生命周期证据"：

文件 说明
run.json 这次运行是谁、什么时候、分析哪个 case
preflight-report.json Trace 输入检查结果
analysis-checkpoint.json Agent 阶段产生的分析状态/结果
findings.json 最终 findings
evidence.json 分析过程中形成的证据
validation.json 最终 AnalysisResult 有没有通过契约验证
agent-log.jsonl Agent 运行过程日志
report.html 最终用户看的可视化报告

十二、职责红线（绝对不要搞混）

组件 负责 不负责
Agent 分析、推理、诊断、给 evidence、给 recommendation 不写 HTML、不写 CSS、不画图
Skill 分析方法、专业知识、输出规范、evidence 标准、finding 标准 不写 HTML
Projection 查 DB、算 timeline、算 perf、算 flame tree、整理 view model 不判断"真正原因是什么"、不让 LLM 再分析一次
Renderer Jinja2 render、把数据放进去 不 SQL、不查线程、不判断根因、不选择 finding

十三、类比记忆法

角色 对应组件 职责
记者 Agent 去调查发生了什么、为什么发生、证据是什么、怎么解决，最后写调查结论
资料库 SQLite 保存原始事实
数据编辑 Projection 把资料库里的各种原始数据 + 记者的调查结论，整理成报告需要的图表和字段
排版员 Renderer 把整理好的内容排成 HTML 页面
前端展示 Browser JS 用户打开报告后的放大、缩小、拖时间线、查看火焰图、点击 evidence 等交互

十五、面试核心答案

这个系统把"分析"和"展示"彻底解耦：Agent 通过 Skill 和 Tool 对 Trace 做分析，输出经过校验的结构化 AnalysisResult；报告生成阶段由 Projection 层重新读取校验后的分析结果、Evidence 和 SQLite 中的 Trace 数据，确定性地计算时间线、性能和火焰图等视图数据，再交给 Jinja2 渲染成自包含 HTML，浏览器端 JavaScript 只负责交互式可视化。因此模型不直接生成 HTML，也不负责图表数据计算。

十六、各组件职责一句话总结

组件 一句话
Skill 决定 Agent"分析出什么"（分析方法 + 输出规范）
AnalysisResult 决定报告"讲什么"（结构化诊断结果）
Projection 决定报告"展示什么数据"（页面数据计算）
Jinja2 决定报告"长什么页面"（HTML 模板渲染）
浏览器 JS 决定报告"怎么交互"（交互式可视化）

最核心的一条线：

Skill → Agent 分析 → AnalysisResult → Validation → Projection → Jinja2 → HTML → 浏览器 JS 可视化

SQLite 是贯穿其中的数据事实源。
