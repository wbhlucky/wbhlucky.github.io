MCP 复盘：tools/list、tools/call 与协议真正标准化的那一层

1. MCP 到底标准化了什么

MCP 可以先记成一句话：

MCP 标准化了 Host / Client 与 Server 之间如何发现工具、描述工具、调用工具以及返回工具结果。

它不是 LLM 本身的协议，也不是统一所有厂商的原生 Function Calling API。

最核心的两个方法：

tools/list  -> 我有哪些工具？
tools/call  -> 执行哪个工具？

可以把它类比成：

Tool List = 菜单
Tool Call = 点菜
Tool Result = 上菜

2. tools/list：工具发现

tools/list 用来让 MCP Server 告诉 MCP Client：

“我有哪些工具，以及这些工具怎么调用、可能返回什么结构。”

典型 Tool Definition：

{
  "name": "query_trace_sql",
  "description": "Query trace data using read-only SQL",
  "inputSchema": {
    "type": "object",
    "properties": {
      "sql": {
        "type": "string"
      },
      "limit": {
        "type": "integer"
      }
    },
    "required": ["sql"]
  },
  "outputSchema": {
    "type": "object",
    "properties": {
      "rows": {
        "type": "array"
      }
    }
  }
}

Tool Definition 最重要的字段

字段 含义
name 工具名字 / 唯一标识
description 告诉模型这个工具能干什么
inputSchema 规定调用工具时 arguments 应该长什么样
outputSchema 可选；规定结构化工具结果 structuredContent 应该长什么样
title / annotations / icons / _meta 其他可选元数据

因此：

tools/list
    ↓
Tool Definition
    ├── name
    ├── description
    ├── inputSchema
    └── outputSchema（可选）

最重要的理解

inputSchema
    -> 我怎么调用你？

outputSchema
    -> 你调用完以后，结构化结果应该是什么形状？

注意：outputSchema 是契约，不是实际返回的数据。

3. tools/call：真正执行工具

当模型通过 Host 决定调用一个工具时，Host / MCP Client 会向 Server 发起 tools/call。

例如：

{
  "method": "tools/call",
  "params": {
    "name": "query_trace_sql",
    "arguments": {
      "sql": "SELECT * FROM slices LIMIT 20"
    }
  }
}

所以：

tools/list
    -> “有哪些工具？”

tools/call
    -> “现在执行这个工具，参数是这些。”

4. Tool Result / CallToolResult 是什么

Server 执行完真正的 Tool 后，会把结果按照 MCP 定义的 CallToolResult 形式返回给 Client。

核心可以理解为：

{
  "content": [
    {
      "type": "text",
      "text": "查询到了 20 条记录"
    }
  ],
  "structuredContent": {
    "rows": [
      {
        "ts": 123,
        "dur": 456
      }
    ]
  },
  "isError": false
}

方向是：

MCP Server
    ↓
CallToolResult
    ↓
MCP Client

它不是 LLM 的最终回答，而是 MCP 层的工具执行结果。

5. content、structuredContent 到底有什么区别

这是最容易混淆的地方。

5.1 content

content 是 Tool 执行结果的可读内容，主要面向模型消费，也可以被 Host / UI 直接展示。

例如：

{
  "content": [
    {
      "type": "text",
      "text": "RenderThread 是主要 CPU 热点，累计耗时 83ms"
    }
  ]
}

它不是模型自己“推理出来”的。

而是：

Tool 执行
    ↓
Server 拿到真实执行结果
    ↓
Server 按自己的逻辑组装成可读内容
    ↓
content

所以：

content 写什么，取决于 MCP Server 的实现逻辑。

它可以是文本，也可以是其他 MCP 支持的内容块。

5.2 structuredContent

structuredContent 是 Tool 结果的结构化 JSON 数据，主要方便 Host / Client / 前端程序直接解析和消费。

例如：

{
  "structuredContent": {
    "hotspots": [
      {
        "thread": "RenderThread",
        "duration_ms": 83
      }
    ],
    "totalDuration": 120
  }
}

程序可以直接：

result["hotspots"][0]["duration_ms"]

而不需要从自然语言：

“RenderThread 是主要 CPU 热点，累计耗时 83ms”

里再解析数字。

5.3 两者不要记成“人 vs LLM”

错误理解：

content -> 给人
structuredContent -> 给 LLM

更准确：

content
    -> 非结构化 / 可读 / 主要让模型消费

structuredContent
    -> 结构化 / 主要让 Host、Client、程序、UI 直接消费

前端究竟展示什么，不是 MCP 强制规定的；Host 可以：

只展示 content
只使用 structuredContent
两者结合

6. outputSchema、structuredContent、content 三者关系

这是最应该记住的一组关系：

Tool Definition
    ↓
outputSchema
    ↓
“你应该返回什么结构”

Tool 执行
    ↓
structuredContent
    ↓
“这一次实际返回的数据”

Tool 执行
    ↓
content
    ↓
“把这次结果用可读方式表达出来”

所以：

outputSchema = 契约
structuredContent = 实际结构化数据
content = 可读表示

最像普通函数里的关系：

def get_temperature(city: str) -> TemperatureResult:
    ...

对应：

name
    -> 函数叫什么

description
    -> 函数干什么

inputSchema
    -> 参数怎么传

outputSchema
    -> 返回值是什么结构

structuredContent
    -> 本次实际返回值

content
    -> 返回值的可读表达

outputSchema 并不是所有工具都必须有，所以有些 Tool 的 Tool List 只有：

name
+ description
+ inputSchema

依然可以正常工作。

7. Host / Client / Server 分别是什么

Host

Host 是承载整个 AI 应用 / Agent 的主体。

例如：

Claude Desktop
Claude Code
Cursor
VS Code + AI Agent
你自己写的 Trace Agent

Host 里面可以有：

Host
├── LLM
├── Agent Loop
├── MCP Client
├── Context 管理
├── Tool 调度
└── 权限控制

所以：

Host = 整个 AI 应用 / Agent 宿主。

MCP Client

Client 是 Host 里面负责和某个 MCP Server 建立 MCP 通信的组件。

一个 Host 可以连接多个 Server：

Host
├── MCP Client A ── MCP Server A
├── MCP Client B ── MCP Server B
└── MCP Client C ── MCP Server C

所以：

Client 不是整个 Agent，而是 Host 中负责 MCP 通信的一端。

MCP Server

Server 是把能力通过 MCP 标准暴露出去的一端。

例如 Trace Server：

Trace MCP Server
├── query_trace_sql
├── get_trace_overview
├── inspect_cpu
├── inspect_sched
└── inspect_render

它负责：

tools/list
    ↓
返回 Tool Definition

tools/call
    ↓
执行 Tool
    ↓
返回 CallToolResult

Server 不需要知道 Host 最终使用的是 Claude、GPT、Gemini 还是其他模型。

8. Host / Client / Server 的完整运行链路

以 Trace Agent 为例：

                    Host
        ┌──────────────────────────┐
        │                          │
        │     Trace Analysis Agent │
        │                          │
        │          LLM             │
        │           ↑↓             │
        │       Agent Loop         │
        │           ↑↓             │
        │       MCP Client         │
        └───────────┼──────────────┘
                    │
              MCP Protocol
                    │
        ┌───────────↓──────────────┐
        │      MCP Server          │
        │                          │
        │  query_trace_sql         │
        │  inspect_perf_profile    │
        │  inspect_sched           │
        └──────────────────────────┘

实际过程：

第一步：发现工具

Client → Server
        tools/list

Server 返回：

query_trace_sql
inspect_perf_profile
inspect_sched

第二步：Host 把 Tool Definition 提供给模型

Server
  ↓
MCP Client
  ↓
Host
  ↓
LLM

模型因此知道：

有什么工具
工具做什么
需要什么输入
可选地知道结构化输出长什么样

第三步：模型决定调用

模型在模型侧产生 Tool Calling 意图，例如：

{
  "name": "query_trace_sql",
  "arguments": {
    "sql": "SELECT ..."
  }
}

Host / MCP Client 再把它转成 MCP 的：

{
  "method": "tools/call",
  "params": {
    "name": "query_trace_sql",
    "arguments": {
      "sql": "SELECT ..."
    }
  }
}

第四步：Server 执行

MCP Server
    ↓
query_trace_sql()
    ↓
SQLite / Trace 数据

第五步：Server 返回 Tool Result

Server
  ↓
CallToolResult
  ↓
Client

第六步：Host 把结果送回 Agent Context

MCP Server
    ↓
MCP Client
    ↓
Host
    ↓
Agent Context
    ↓
LLM

模型再根据结果决定：

证据足够 → 继续分析 / 输出结论
证据不足 → 再调用其他 Tool

因此 MCP Tool Loop 可以理解为：

LLM
 ↓
Tool Call 意图
 ↓
MCP Client
 ↓
tools/call
 ↓
MCP Server
 ↓
执行 Tool
 ↓
CallToolResult
 ↓
MCP Client
 ↓
Host Context
 ↓
LLM
 ↺

9. MCP 与 LLM Function Calling 的关系

一个非常关键的理解：

MCP 统一的是“工具侧协议”，不是所有 LLM 厂商的原生 Tool Calling API。

例如不同模型供应商可能存在不同的模型接口：

OpenAI API
Anthropic API
Gemini API
DeepSeek API
...

Host 通常还需要一个 LLM Adapter，把模型侧的 Tool Calling 表达转换成统一的内部 Agent 表达，再由 MCP Client 去调用 MCP Server。

可以理解成两层：

                 LLM / Model Layer
                        ↑↓
               LLM Function Calling
                        ↑↓
                     Host
                        ↑↓
                  MCP Client
                        ↑↓
                  MCP Protocol
                        ↑↓
                  MCP Server
                        ↑↓
                      Tool

所以 MCP 并不是：

“让所有 LLM API 都变成一样”

而是：

“让工具提供侧和工具调用侧之间有统一的标准协议”

10. 一张最值得记住的总表

概念 一句话理解
Host 整个 AI 应用 / Agent 宿主
MCP Client Host 中负责连接 MCP Server 的协议组件
MCP Server 对外暴露 Tools / Resources / Prompts 等能力的一端
tools/list “你有哪些工具？”
Tool Definition 工具说明书：name + description + inputSchema + 可选 outputSchema
tools/call “执行这个工具，并传这些参数。”
CallToolResult Server 执行 Tool 后返回给 Client 的标准工具结果
content 可读的 Tool 结果，主要供模型消费，也可被 UI 展示
structuredContent 结构化的 Tool 结果，主要供 Host / Client / 程序直接解析
outputSchema structuredContent 的输出契约
isError 本次 Tool 调用是否发生工具级错误
MCP Host / Client ↔ Server 之间的标准通信协议
LLM Function Calling 模型 ↔ Host 之间的模型侧工具调用接口

12. 一个最终的认知边界

最容易混淆的是三个层次：

① LLM 层
   模型决定：我要不要调用工具？调用哪个工具？参数是什么？

② MCP 层
   标准化：工具怎么发现、怎么调用、结果怎么返回。

③ Tool 实现层
   真正执行 SQL、读文件、查 Trace、调用 API 等业务逻辑。

因此：

MCP 不负责“推理”，MCP 负责把模型想调用的外部能力，以统一协议连接起来。
