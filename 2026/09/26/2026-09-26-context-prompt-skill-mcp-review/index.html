上下文、提示词、Skill 与 MCP 复盘：模型这一轮到底看到了什么

这份笔记用于复盘 Agent Runtime 中几个最容易混淆的概念：Context、Prompt、System Prompt、User Prompt、Tool、Skill、Memory、MCP。

核心目标不是记 API，而是搞清楚：

模型这一轮到底看到了什么、这些内容从哪里来、模型如何获得额外知识、模型如何调用工具，以及 MCP 到底标准化了哪一层。

1. 先建立最核心的关系

可以先记住这张图：

                    Agent Runtime
                         │
                         ▼
                  ┌─────────────┐
                  │   Context   │
                  │ 模型这一轮   │
                  │ 真正看到的   │
                  └─────────────┘
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
   System Prompt     User Prompt     Tool Results
          │              │              │
          │              │              └─ 工具执行产生的事实
          │              └─ 本次任务输入
          └─ 行为规则、角色、能力说明

             Context 中还可能出现：

        Skill 正文 / Memory / History / Evidence

最重要的一句话：

Context 是“大容器”，Prompt 是其中用于指导模型的文本，System Prompt 和 User Prompt 是 Prompt 的不同层次。

因此：

Context ≠ Prompt
Prompt ⊂ Context

更准确地说，Context 是模型推理时接收到的完整上下文集合，而 Prompt 是其中用于给模型指令和任务信息的部分。

2. 什么是 Context？

2.1 Context 就是“这一轮模型实际拿到的全部信息”

例如一个 Agent 某一轮可能收到：

System Prompt
+
User Prompt
+
历史对话
+
Skill 正文
+
Memory
+
工具定义 / Tool Schema
+
前置证据
+
工具调用结果

这些内容共同构成模型这一轮的 Context。

所以分析 Agent 最重要的问题之一不是：

“仓库里有什么知识？”

而是：

“这些知识最终有没有进入 Context？”

仓库里存在一个文件，并不代表模型就看到了这个文件。

2.2 Context 有“静态部分”和“动态部分”

可以粗略理解成：

初始 Context
├── System Prompt
├── User Prompt
├── Tool Schema
├── Skill Metadata
└── 其他初始化信息

随着 Agent Loop 运行
        ↓
Context 动态追加
├── Tool Call
├── Tool Result
├── Skill 正文
├── Memory
├── 中间分析结果
└── 后续消息

所以 Agent 不是“一次把所有东西塞给模型”，而是：

随着推理和工具调用不断扩展 Context。

这也是为什么 Agent 会出现 Context Budget、Context Window、Token Cost、历史裁剪等工程问题。

3. 什么是 Prompt？

Prompt 可以理解成：

告诉模型“你是谁、应该怎么做、现在要解决什么问题”的文字指令。

常见的 Prompt 层次：

System Prompt
    ↓
规定角色、行为、规则、约束

User Prompt
    ↓
告诉模型这次具体要做什么

Developer Prompt / Instruction
    ↓
某些系统中还会有更高优先级的开发者规则

不同平台的消息层命名可能不同，但核心思想是一致的：

不同消息层具有不同的指令优先级和职责。

4. System Prompt 到底是什么？

System Prompt 可以理解为 Agent 的“基础操作规范”。

例如：

你是一个 Trace 性能分析 Agent。

分析时必须：
1. 先获取基础信息
2. 再检查关键事件
3. 给出证据链
4. 不允许无证据猜测
5. 最终按照指定 Schema 输出

这些内容主要是在规定：

你是谁
你能做什么
你应该怎么推理
你有哪些限制
输出必须遵守什么格式
有哪些能力可以使用

所以 System Prompt 更偏向：

规则、方法、行为约束、能力说明。

5. User Prompt 是什么？

User Prompt 更偏向“本次任务”。

例如：

{
  "trace_id": "xxx",
  "scenario": "completion-latency",
  "symptom": "页面打开较慢",
  "device": "xxx"
}

再加一句：

请分析本次 Trace 并给出根因。

它回答的是：

“这一次具体分析什么？”

因此可以记成：

System Prompt = 怎么做
User Prompt   = 做什么
Context       = 这一轮模型总共看到了什么

这是一组非常重要的概念区分。

6. Skill 到底是什么？

Skill 最好不要理解成：

“一大段固定 Prompt。”

更准确的理解是：

Skill = 一组面向特定任务的专业知识 / 方法论 / 操作说明，通常以文件形式存在，并支持按需加载。

例如：

completion-latency-analysis
├── SKILL.md
├── references/
├── examples/
└── scripts/

里面可能写：

什么叫 completion latency
应该观察哪些 trace event
如何定义起止点
哪些证据可以支持某个根因
常见误区是什么

7. Skill 的关键设计：渐进式披露（Progressive Disclosure）

成熟的 Skill 架构通常不是：

启动 Agent
    ↓
把整个 Skill 文件全部塞进 System Prompt

而更像：

启动 Agent
    ↓
只告诉模型有哪些 Skill
以及每个 Skill 是干什么的
    ↓
模型发现当前任务需要某个 Skill
    ↓
读取对应 SKILL.md
    ↓
SKILL.md 正文进入 Context
    ↓
需要进一步细节时
再读取 references / examples / scripts

也就是：

Level 1：Metadata
    name
    description
        ↓
    进入初始 Context

Level 2：SKILL.md 正文
        ↓
    按需读取
        ↓
    进入 Context

Level 3：references / resources
        ↓
    真正需要时再读取

因此：

Skill Metadata 可以出现在 System Prompt 中，但 Skill 正文不等于 System Prompt。

这是非常重要的区别。

8. 所以“模型怎么拿到 Skill 正文？”

核心就是：

需要一个可以把 Skill 文件内容读出来，并把读取结果返回给模型的机制。

最简单的形式就是文件读取工具：

模型
 ↓
Read(".../SKILL.md")
 ↓
Runtime / Tool
 ↓
读取文件
 ↓
返回 SKILL.md 内容
 ↓
Tool Result
 ↓
进入 Context

因此：

Skill Metadata
= 告诉模型“有这个 Skill”

Read / Skill Loader
= 让模型“拿到这个 Skill 的正文”

这两者不是一回事。

9. Tool 是什么？

Tool 可以简单理解成：

模型能够请求 Agent Runtime 执行的一项外部能力。

例如：

query_trace_sql
read_file
search_web
execute_python
inspect_perf_profile

模型本身只负责生成：

{
  "tool": "query_trace_sql",
  "arguments": {
    "sql": "SELECT ..."
  }
}

真正执行 SQL 的不是模型，而是 Runtime / Tool。

执行完成后：

Tool
 ↓
执行
 ↓
Tool Result
 ↓
进入 Context
 ↓
模型继续推理

所以 Tool 的作用是：

把模型从“只能处理已有文本”，扩展成“可以获取信息和执行动作”。

10. Tool 和 Skill 的区别

这是 Agent 开发中非常容易混淆的一对概念。

Skill

偏“怎么做”：

性能分析的方法论
诊断步骤
判断规则
经验
注意事项

Tool

偏“做什么”：

查询 Trace
读取文件
执行 SQL
获取 profile
计算指标

可以记成：

Skill = 知识 / 方法论
Tool  = 能力 / 动作

进一步可以理解成：

Skill 告诉模型：
“应该检查哪些东西、怎么判断”

Tool 帮模型：
“真的去把这些东西查出来”

11. Evidence 又是什么？

Evidence 是本次任务真正产生的事实依据。

例如：

Main Thread
Duration = 52ms
CPU = 100%

TaskRunner
Duration = 31ms

NativeWindowFlushBuffer
Duration = 18ms

这些不是方法论，而是本次 Trace 的真实数据。

所以可以区分：

Skill
    ↓
告诉模型“怎么看”

Tool
    ↓
帮模型“拿数据”

Evidence
    ↓
本次分析“实际拿到了什么事实”

LLM
    ↓
结合方法论 + 事实进行推理

12. Memory 和 Skill 又有什么区别？

Skill

更偏长期、稳定、结构化的领域知识：

如何分析 completion latency
如何判断 frame jank
如何解读某类 Trace

Memory

更偏“过去发生过什么，以及过去形成了什么经验”。

例如：

过去某类 Trace 经常出现某种模式
过去处理某种问题时，某个证据特别有效
某类场景之前已经验证过某种诊断路径

因此可以粗略理解成：

Skill  = 专业知识
Memory = 历史经验

两者都可以最终进入 Context，供模型推理使用。

13. MCP 到底是什么？

MCP 最容易被误解成：

“模型调用工具的统一协议。”

这个说法不够准确。

更准确地说：

MCP（Model Context Protocol）主要标准化的是“AI 应用 / Agent 与外部能力提供方之间，如何发现、描述、调用和返回上下文”的协议。

例如一个 MCP Server 可以暴露：

Tools
Resources
Prompts

其中最常被 Agent 使用的是 Tools。

例如：

MCP Server
   │
   ├── query_trace_sql
   ├── get_trace_overview
   └── inspect_perf_profile

客户端可以按 MCP 规定的方式发现这些能力以及对应 Schema。

14. MCP 真正标准化了什么？

核心可以理解为三个层面：

1. 能力如何描述
2. 能力如何发现
3. 能力如何调用 / 返回结果

例如一个 Tool 可以有统一的结构化描述：

{
  "name": "query_trace_sql",
  "description": "查询 Trace 数据",
  "inputSchema": {
    "type": "object",
    "properties": {
      "sql": {
        "type": "string"
      }
    }
  }
}

这样 Agent Runtime 不需要为每个工具重新设计一套完全不同的“工具描述格式”。

15. MCP 并不等于 LLM API 协议

这是另一个特别容易混淆的点。

可以把系统分成两段：

         模型侧                         工具侧

LLM API / Model Protocol        MCP
       │                          │
       ▼                          ▼
模型如何表达 Tool Call       Agent 如何发现/调用外部能力

MCP 解决的是工具生态这一侧的问题。

而不同模型厂商的 API 历史上可能有不同的消息格式、Tool Calling 格式、响应结构等。

因此不能简单理解成：

MCP = 所有模型都直接原生理解的语言

更准确的是：

Agent Runtime
    ↓
MCP Client
    ↓
统一连接 MCP Server
    ↓
拿到工具定义 / Tool Result
    ↓
Runtime 再把这些信息适配成当前 LLM API 所需要的格式
    ↓
LLM

所以：

MCP 可以统一“工具侧”的协议，但不意味着所有 LLM API 的消息协议因此自动变成完全相同。

16. 为什么说 MCP 的价值在于“工具侧统一”？

传统方式经常是：

Agent A ── 自己实现 ── Tool A
Agent B ── 自己实现 ── Tool A
Agent C ── 自己实现 ── Tool A

工具提供方需要针对不同 Agent 集成方式维护很多重复接口。

采用 MCP 后，可以更接近：

                    ┌── Agent A
                    │
MCP Server ──────────┼── Agent B
                    │
                    └── Agent C

多个兼容 MCP 的客户端可以按同一套 MCP 方式发现和调用工具。

因此 MCP 的重要价值之一是：

把“工具提供方”和“Agent 应用”的耦合降低。

17. 为什么还会出现 Adapter？

因为“工具侧统一”和“模型侧统一”不是同一回事。

假设 MCP Client 已经拿到了：

name
├── query_trace_sql
└── inputSchema

接下来仍然需要把这些工具信息交给具体的模型 API。

不同模型 SDK / API 可能需要不同的消息结构。

所以可能存在：

MCP Tool Schema
      ↓
LLM Adapter
      ↓
OpenAI-style Tool Calling
Anthropic-style Tool Calling
其他模型 API 的 Tool Calling

这也是为什么“有 MCP”并不自动意味着 Agent 可以无条件直连任意模型。

18. “模型支持 MCP”到底是什么意思？

严格来说，需要区分：

MCP Server 支持

工具服务按照 MCP 暴露能力。

MCP Client 支持

Agent Runtime 可以连接 MCP Server，发现并调用能力。

Model 原生支持

模型 / 模型平台自身是否直接理解 MCP。

在工程实践中，更常见的是：

模型
 ↓
LLM API
 ↓
Agent Runtime
 ↓
MCP Client
 ↓
MCP Server
 ↓
Tool

所以最关键的不是一句“模型支不支持 MCP”，而是看：

整个 Agent Runtime 是否已经帮你把 MCP 能力接入当前模型调用链。

19. Tool Schema、MCP Schema、LLM Tool Calling 是什么关系？

可以把它们分成三个层次：

                 MCP
        统一工具能力的描述/调用
                 │
                 ▼
         MCP Tool Schema
                 │
                 ▼
          Agent Runtime
                 │
          做协议适配 / 映射
                 │
                 ▼
          LLM Tool Calling
                 │
                 ▼
              Model

其中最容易混淆的是：

MCP 的 Tool Schema 和某一家模型 API 的 Tool Calling Schema 不是同一个东西。

它们可以表达类似信息，但属于不同协议层。

20. 一个完整的 Agent Loop 怎么串起来？

可以把整个流程记成：

用户任务
   ↓
User Prompt
   ↓
Agent Runtime 构造初始 Context
   │
   ├── System Prompt
   ├── User Prompt
   ├── Tool Schema
   ├── Skill Metadata
   └── Memory / Evidence（如果有）
   ↓
LLM
   ↓
模型判断下一步
   │
   ├── 直接回答
   │
   └── Tool Call
          ↓
       Tool / MCP
          ↓
       执行真实操作
          ↓
       Tool Result
          ↓
       追加 Context
          ↓
       LLM 再次推理
          ↓
       ……循环……
          ↓
       Final Answer

而 Skill 的按需加载可以插在中间：

LLM
 ↓
发现需要某 Skill
 ↓
Read / Skill Loader
 ↓
SKILL.md
 ↓
Skill 正文进入 Context
 ↓
继续推理

21. 用一句话区分这几个概念

概念 核心问题 简单理解
Context 模型这一轮看到了什么？ 总上下文
Prompt 应该怎么指导模型？ 指令文本
System Prompt Agent 应该遵守什么规则？ 系统级规则
User Prompt 这次具体做什么？ 当前任务
Skill 这个领域应该怎么分析？ 专业方法论
Tool 怎么去获取数据/执行动作？ 外部能力
Evidence 这次实际拿到了什么事实？ 证据
Memory 过去积累了什么经验？ 历史经验
MCP Agent 和外部能力如何标准化连接？ 工具生态协议

22. 最重要的几个认知

认知 1

文件存在 ≠ 模型看到了文件。

必须存在一条真正的链路：

文件
 ↓
读取机制
 ↓
Tool Result / Message
 ↓
Context
 ↓
模型

认知 2

Skill Metadata 和 Skill 正文是两层东西。

Metadata
= 让模型知道“有什么 Skill”

正文
= 让模型知道“这个 Skill 具体怎么做”

认知 3

Context 比 Prompt 大。

Context
├── Prompt
├── Tool Schema
├── History
├── Skill
├── Memory
├── Evidence
└── Tool Results

认知 4

Tool 是执行层，Skill 是知识层。

Skill → 告诉模型怎么判断
Tool  → 帮模型真的去查

认知 5

MCP 主要解决工具连接与描述标准化，不等于统一所有 LLM API。

MCP
= 工具生态侧的标准化

LLM Adapter
= 模型调用协议侧的适配

23. 最后用一个完整例子理解

假设任务是：

“分析一次 App 启动慢的问题。”

第一阶段：初始 Context

System Prompt
└── 你是性能分析 Agent，必须基于证据分析

User Prompt
└── trace_id=123，scenario=cold-start

Skill Metadata
└── cold-start-analysis

Tool Schema
├── query_trace_sql
├── get_trace_overview
└── inspect_perf_profile

模型此时知道：

我是谁
任务是什么
有哪些 Skill
有哪些 Tool

但它未必已经知道完整的方法论。

第二阶段：读取 Skill

模型发现需要 cold-start 方法论：

Read(SKILL.md)

然后：

SKILL.md
 ↓
Tool Result
 ↓
Context

此时模型真正获得：

启动耗时应该怎么定义
应该观察哪些阶段
哪些事件属于关键路径
如何定位瓶颈

第三阶段：调用 Tool

模型继续：

query_trace_sql(...)

工具返回：

Main Thread = 72ms
TaskRunner = 31ms
CPU contention = high

这些事实再次进入 Context。

第四阶段：模型推理

现在模型同时拥有：

Skill
= 怎么分析

Evidence
= 本次发生了什么

System Prompt
= 必须遵守什么规则

User Prompt
= 用户要解决什么问题

最后才能形成比较完整的分析。

24. 最终记忆口诀

Context：模型看到了什么
Prompt：告诉模型怎么做
System：长期规则
User：当前任务
Skill：专业方法论
Tool：外部能力
Evidence：本次事实
Memory：历史经验
MCP：工具生态的标准连接协议

再压缩成一句：

Prompt 管“怎么做”，Skill 提供“专业上怎么做”，Tool 负责“真的去做”，Evidence 提供“做出来的事实”，Memory 提供“以前做过的经验”，Context 则是这一轮模型最终能看到的全部内容；MCP 主要负责把 Agent 与外部工具能力标准化连接起来。
